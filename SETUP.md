# Fall Detection Project Setup

This document is the operational setup guide for the Fall Detection project. It is written so a developer or coding agent can prepare the existing project, run its tests, train the real model, start the services, and launch the Wokwi simulation without reconstructing the setup from the source tree.

No application code is generated by these instructions. The commands install dependencies and create ignored datasets, models, reports, and build output.

## Project Layout

| Path | Purpose |
| --- | --- |
| `FallDetection.ino` | ESP32 firmware: sensor sampling, threshold detection, SOS, LEDs, buzzer, MQTT publishing |
| `diagram.json` | Wokwi ESP32, MPU6050, button, buzzer, and LED wiring |
| `wokwi.toml` | Wokwi firmware and ELF paths |
| `.vscode/arduino.json` | Arduino board and build-output configuration |
| `dashboard/` | React/Vite caregiver dashboard |
| `ml/train.py` | SisFall parser, feature extraction, Random Forest training, and LOSO evaluation |
| `ml/server.py` | MQTT inference service |
| `ml/tests/` | Python unit and integration tests |
| `ml/README.md` | ML-specific reference |
| `DESIGN.md` | Dashboard design tokens and visual language |

## Architecture

```text
MPU6050 -> ESP32 firmware -> HiveMQ MQTT broker -> React dashboard
                              |
                              +-> ml/server.py -> ML_CONFIRMED_FALL alert
```

The firmware samples acceleration at approximately 10 Hz and publishes a 30-sample, 3-axis window after detecting a free-fall/impact sequence. The ML pipeline is trained on SisFall data decimated from 200 Hz to 10 Hz, so its inference contract matches the firmware: exactly 30 numeric `[ax, ay, az]` samples, representing approximately three seconds.

## Required Software

### Windows and VS Code

Install:

1. Visual Studio Code.
2. The Microsoft Arduino extension.
3. The Wokwi Simulator extension.
4. WSL2 with an Ubuntu distribution.

The Arduino/Wokwi portion is configured for the `DOIT ESP32 DEVKIT V1` board. The Wokwi simulation is normally launched from VS Code on Windows. The Python ML service and React dashboard can run inside WSL.

From PowerShell, confirm that Ubuntu is available:


Check the tools:

```bash

```

### Proven Arduino CLI setup in WSL (works for this project)

The VS Code Arduino extension can fail or misconfigure the board path on some machines. The working alternative used for this project is to install and use the Arduino CLI directly inside WSL.

```bash
# from Ubuntu in WSL
curl -fsSL https://raw.githubusercontent.com/arduino/arduino-cli/master/install.sh | bash
export PATH="$HOME/.local/bin:$PATH"
arduino-cli version
arduino-cli core update-index
arduino-cli core install esp32:esp32
arduino-cli lib install 'PubSubClient'
arduino-cli lib install 'Adafruit MPU6050'
```

The project uses these exact libraries and the board FQBN:

```text
Board: esp32:esp32:esp32doit-devkit-v1
Libraries: PubSubClient, Adafruit MPU6050
```

This path is reliable when the VS Code Arduino extension is broken, stale, or unable to resolve the board configuration.

## Train on the Real Dataset

Run the real-data training command from the repository root:

```bash
python ml/train.py \
  --data-dir SisFall_dataset \
  --model-output ml/fall_detection_model.joblib \
  --artifacts-dir ml/artifacts
```

This command:

1. Discovers canonical SisFall recordings recursively.
2. Selects MMA8451Q accelerometer columns 6-8.
3. Converts raw values using `1/1024 g` per LSB.
4. Decimates 200 Hz recordings to 10 Hz.
5. Creates 30-sample windows with 15-sample overlap.
6. Extracts the seven deployed features.
7. Runs Leave-One-Subject-Out validation.
8. Fits a final model on all validated windows.
9. Writes the model and evaluation artifacts.

Generated files:

| File | Purpose |
| --- | --- |
| `ml/fall_detection_model.joblib` | Metadata-wrapped production inference model |
| `ml/artifacts/evaluation.json` | Machine-readable configuration, counts, confusion matrix, and metrics |
| `ml/artifacts/evaluation.md` | Human-readable evaluation report |

The model and artifacts are ignored by Git. SisFall metrics describe performed falls from a waist-mounted sensor and must not be presented as wrist/pendant or real-world unobserved-fall accuracy.

Use three processes:

3. Windows VS Code: compile firmware, then start Wokwi.

### Firmware compilation and Wokwi

This repository is configured for the Wokwi build artifacts to be generated in the repo root `build/` directory. The exact working command used for this project is:

```bash
cd /mnt/c/Users/KESHAV/Documents/IOEProject/FallDetection
mkdir -p build
arduino-cli compile --fqbn esp32:esp32:esp32doit-devkit-v1 --build-path build FallDetection.ino
ls -l build
```

Verify that the build directory contains the generated binaries, including:

```text
build/FallDetection.ino.bin
build/FallDetection.ino.elf
```

Then in VS Code on Windows:

1. Open `FallDetection.ino` if needed.
2. Start Wokwi using `Wokwi: Start Simulator`.
3. Confirm the simulator loads the binaries defined in `wokwi.toml`.
4. Open the Serial Monitor.

The Wokwi firmware uses `Wokwi-GUEST` Wi-Fi and publishes to the public HiveMQ broker. In the simulator, move the MPU6050 acceleration controls to create a low-magnitude free-fall followed by an impact, or press the red SOS button.

> If the Arduino extension is still failing, keep the Arduino CLI path above as the canonical setup. It is the proven, working route for this repo and the one we used to complete the installation and firmware compile path.

The firmware pin mapping is:

| Device | ESP32 pin |
| --- | --- |
| MPU6050 SDA | GPIO21 |
| MPU6050 SCL | GPIO22 |
| Buzzer | GPIO25 |
| SOS button | GPIO4 |
| Red LED | GPIO27 |
| Green LED | GPIO26 |

The local threshold path detects free fall below `0.4 g`, then impact above `1.8 g` within the configured window. After the impact it gives the wearer an 8-second cancellation period before publishing the confirmed alert.

## Troubleshooting

### `No such file or directory: ml/fall_detection_model.joblib`

Run the real training command first. The service intentionally refuses to start without a model.

### `SisFall dataset directory not found`

Confirm that the extracted path is exactly `SisFall_dataset/` at the repository root, not only `~/sisfall-archive/` or a nested duplicate directory.

### scikit-learn import or DLL errors

Activate the WSL virtual environment and run the Python commands inside WSL:

```bash
source ~/.venvs/falldetection/bin/activate
python -c "import sklearn; print(sklearn.__version__)"
```

### `vite` or `oxlint` is not recognized

Run `npm install` from `dashboard/`, then retry `npm run build` or `npm run lint`.

### Wokwi cannot find the firmware binary

Compile `FallDetection.ino` first. Wokwi reads the paths configured in `wokwi.toml`, including `build/FallDetection.ino.bin` and its ELF file.

### Dashboard shows no data

Check that the browser can reach HiveMQ over WebSockets, that the firmware or MQTT test publisher is active, and that all processes use the exact topic names documented above. The dashboard does not invent sensor data on its own.

### Live feed works but Confirmed Alerts is empty

The dashboard uses two separate MQTT topics:

```text
ioe-lab/fall-detection/team41/sensor_data
ioe-lab/fall-detection/team41/alert
```

If the live graph updates but the alert panel still says `System is monitoring. No falls detected.`, the dashboard connection is working and no new alert has arrived yet. Press the Wokwi SOS button after the dashboard shows `Connected to HiveMQ`, or complete the free-fall/impact sequence and wait for the 8-second confirmation window.

MQTT messages are not retained by this demo. Alerts published before the dashboard connected will not appear later; trigger the SOS or fall event again after the dashboard is connected.
